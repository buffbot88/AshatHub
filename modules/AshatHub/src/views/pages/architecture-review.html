Architecture Review

ASHAT Hub · v5.6

Surface friction across 24 modules · 12 controllers · 6 models · 10 core classes · 3 JS files

Codebase at a glance

ASHAT Hub is a browser-based AI coding platform. The PHP backend follows a flat MVC pattern with static facades everywhere — no DI container, no service layer, and no middleware other than the Router's named-middleware stack. Models are anemic SQL wrappers. The only documented seam is DatabaseInterface (with an InMemoryDatabase for testing). Controllers read $_POST and $_GET directly. Views mix HTML and PHP with extract()-based variable injection.

1. Static Facade Ocean

Deepen by introducing a proper request context

Strong

Files involved

src/Core/Auth.php — static: login, register, logout, user(), check(), role(), hasRole(), requireRole()
src/Core/Session.php — static: start(), flash(), csrfToken(), assertCsrf(), destroy()
src/Core/Response.php — static: json(), redirect(), back(), jsonBody()
src/Core/View.php — static: render(), partial()
src/Controllers/*.php — all 12 call these statics directly

Problem

Every controller is coupled to four static facades. There is no way to inject a mock session or test response. Auth::requireRole() has an inline new \Controllers\ErrorController() — it instantiates its own collaborator to show errors. Testing a controller means running PHP's real session. The deletion test: removing any one of these facades would require touching every single controller — they distribute complexity instead of concentrating it.

Solution

Introduce a RequestContext object passed to every controller action. Authenticated user, flash messages, and CSRF token live on the context. The Router creates the context once and injects it. Response::redirect() becomes a method on the context or is returned from the action. This gives a single seam: swap the context factory in tests.

2. Anemic Model Layer

Domain logic lives in controllers; models are just SQL wrappers

Strong

Files involved

src/Models/*.php — all 6 are thin SQL wrappers
src/Controllers/BuildsController.php — has acceptAgentBuild() (32 lines of validation)
src/Controllers/AuthController.php — manual $_POST validation
src/Controllers/CommunityController.php — inline validation

Problem

Spec::create() takes raw strings and writes them — no validation. The BuildsController::acceptAgentBuild() is a 32-line validation function embedded in a controller that should be a deep BuildPayload value object. The deletion test: deleting a model file doesn't concentrate logic — it just breaks SQL queries.

Solution

Extract a BuildPayload value object that encapsulates agent-payload validation. Pull validation rules into model-level static methods. Models become the single source of truth for what constitutes valid data.

3. Route Registration Duplication

Two independent paths load the same route files

Worth exploring

Files involved

src/Core/routes.php requires all 5 route files + registers middleware
src/Core/Router.php register() also requires all 5 route files

Problem

Two independent paths load the same route files. The early-return guard prevents double-registration, but a developer adding a new route file needs to know about both paths.

Merge middleware registration into Router::register() so there's one loading path.

4. Unvalidated Input Everywhere

Every controller reinvents $_POST extraction

Strong

Files involved

All 12 controllers + Auth.php contain variations of:
trim((string) ($_POST['x'] ?? '')) — ~40 times across the codebase

Problem

Fragile pattern repeated ~40 times. The $_POST['next'] ?? '/default/' pattern is an open redirect waiting to happen — no whitelist. Every controller is shallow: its interface includes raw HTTP input extraction.

Solution

Introduce a FormRequest object. Controllers define typed parameters. The FormRequest base class handles extraction, applies rules, and exposes validated data.

5. InMemoryDatabase is a 700+ line SQL Parser

The test seam is as complex as the real adapter

Worth exploring

Files involved

src/Core/InMemoryDatabase.php 700+ lines
src/Core/DatabaseInterface.php 5 methods
src/Core/PdoDatabase.php ~50 lines

Problem

700-line SQL parser for a 5-method interface. A shallow module: complex implementation behind a simple interface. The deletion test: losing it forces MySQL in CI.

Replace with per-repository fakes (UserRepository, SpecRepository) backed by arrays — no SQL parsing. 700 lines becomes 7 × ~20-line fakes.

6. View Variable Injection via extract()

Wild variables collide with controller-passed vars

Worth exploring

Abandon extract() and use a dedicated view model class. Eliminates namespace collision and enables type-checking view data.

7. ChatController Does Too Much

AI proxying OR BrainStem config — pick one

Speculative

Move BrainStem config endpoints into AdminController. Extract SSE streaming into SseStreamer utility.

8. JavaScript HTTP Clients Duplicated

Three JS files, three fetch wrappers

Speculative

Consolidate all HTTP into ashatFetch() in app.js. Remove inline fetch calls from agent.js and studio.js.

Top Recommendation

Candidate #1: RequestContext — then Candidate #4: FormRequest.

The static facade ocean is the single biggest obstacle to every other improvement. Introducing a RequestContext that the Router injects into controllers would unblock testing (no real sessions), simplify controllers (one import instead of four), and open the door for FormRequest objects because the context naturally carries the input data.

$ctx = new RequestContext(user: $user, session: $fakeSession);
$req = UpdateProfileRequest::from(['display_name' => 'Alice', 'email' => 'a@b.com']);
$ctrl = new AccountController($ctx);
$result = $ctrl->updateProfile($req);
assert($result instanceof RedirectResponse);
assert($fakeSession->flashes[0] === 'Profile updated.');
